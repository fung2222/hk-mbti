## 1. 逐案根因

### 案 1　見到「1 個測試檔失敗」仍 commit + push

事實：

- 出貨係一個 `execute_code` 腳本（session 訊息 13496），順序係：跑 `sh tools/ui/run.sh` → 印結果 → **無條件** `git add && git commit` → `git push`。腳本冇 `if returncode != 0: sys.exit`。
- 同一格輸出（訊息 13497）：

```text
run.sh rc: 1 | ===== 有 1 個測試檔失敗 ===== | ✗: 冇 ✓
push rc: 0
87e63c6 feat(B 配對): ISTJ 12 篇 ＋ ESTJ 11 篇 → 總 81 篇
```

- `tools/ui/run.sh` 第 25 行嘅字就係「有 N 個測試檔失敗」。代理自己嘅摘要行用 `startswith("✗")` 掃，掃唔到就印「✗: 冇 ✓」。
- 外層 `execute_code` 係 `status: success`（Python 自己冇 throw）。push 嘅 rc 亦係 0。
- 代理之後先承認（訊息 13499）：「上一次跑測試其實有 1 個測試檔失敗（我 push 得太快）」。

機制：

出貨同驗證綁喺同一格，而且失敗唔係停止條件。代理收到三個訊號：runner 話 rc 1、自己嘅 ✗ 掃描話「冇 ✓」、外層工具話成功。求快時揀咗後兩個。`premium-tier.md` 陷阱 8 已經寫明：test throw 會令成個檔 exit 1，但輸出可以冇任何 `✗`；只 grep `✗` 會當全綠。今次腳本剛好就係咁寫，所以「有失敗」同「✗ 冇」可以同時真，而後者被當成放行證。

呢個失敗檔就係案 2 嘅 `pair_test.js`（見下）。產品內容未必錯，但 `main` 由 `87e63c6` 到 `f7c1b1b` 期間測試套係紅嘅。紅套之後任何新失敗都分唔出「舊紅」定「新紅」。

### 案 2　測試寫死「未寫組合 = INTJ×ESTJ」

事實：

- `95de24b` 新增 `tools/ui/pair_test.js`，寫死：

```js
w.openPair("INTJ","ESTJ");
chk("★ 未寫嘅組合 → 出「陸續補上」提示…", /仲喺度寫/.test(...));
```

- 當時第一批只得 INFP 行，INTJ×ESTJ 確實未寫。斷言測嘅係「未寫要有提示」，但樣本係一個會被下一手內容批次寫走嘅 key。
- `87e63c6` 加咗 ESTJ 行（含 `ESTJ|INTJ`），`pair_test.js` 呢個 commit 冇改。`openPair("INTJ","ESTJ")` 會經反向 key 搵到文，唔再出「陸續補上」→ 斷言失效。呢個就係案 1 嗰個紅檔。
- 修正喺之後嘅 `f7c1b1b`：改由 `PAIRS` 動態搵一對真未寫嘅。代理當時講（訊息 13587）：「測試用嘅未寫組合已經被我寫咗」。

機制：

測試把「而家邊對未寫」寫成不變式。內容係分批增長嘅（commit message 自己都寫「陸續補」），所以呢條斷言嘅壽命等於「下一次唔好寫中呢對」。寫內容嘅腳本冇同步改測試，因為代理把測試當成「已存在嘅守門」，唔當成「同資料一齊要維護嘅合約」。`jsdom-functional-testing.md` 已經有同一條教訓（唔好綁死「某型仲未有內容」），但係寫喺 9 章，配對測試係另起爐灶，冇人喺落筆前打開嗰段。

推測：若果案 1 嘅腳本有硬閘，呢條紅會逼代理喺 push 前做案 2 嘅動態化，兩案唔會拆開。

### 案 3　簡體掃描清單把「理」當簡體；同一輪有手誤「为」

事實：

- 第二批內容 `bd7dc4b`（ENFP／ISFJ）commit 時，`pair_test.js` 仲未有簡體守門（守門係下一個 commit `aa507b2` 先加）。即係內容先上船，掃描後補。
- 寫 ESFJ 嗰格（訊息 13478）用咗手寫字元類，入面有「处理」。`理` 繁簡相同，但係字元類一入類就會命中「唔想理你」「道理」「處理」。
- 工具輸出：`簡體字命中: 24`，抽樣 10 個全部係 `理`。`fix` dict 只有 `为→為`。腳本對每個命中字做 `replace(ch, fix.get(ch, ch))`，`理→理` 係 no-op。修完再檢剩 23。少咗 1，同「捉到一個为並換走」一致。
- 代理即時講（訊息 13480）：清單誤收「理」，慶幸 no-op，但捉到「为→為」。其後對用戶嘅總結改口為「同一輪漏捉为」。
- 落庫嘅守門（`aa507b2`，現行 `pair_test.js` L100）有 `为`、冇 `理`。即係最終測試清單已收窄；錯嘅係一次性腳本，而且用完先改。

機制：

清單係憑記憶砌簡體詞，再拆成字元類，冇做兩件事：

1. 負對照：用已知繁體正文跑，必須 0 命中。
2. 正對照：種一個 `为`，必須剛好 1 命中。

假命中一多（24 個，樣板全是 `理`），代理嘅解讀係「清單太寬、replace 係 no-op、可以繼續 push」，而唔係「逐個命中字裁定」。呢個解讀一旦成立，真簡體字會被淹沒；今次 `为` 係因為 fix dict 碰巧有佢先被換走，唔係因為清單驗證過。第二批在掃描存在之前已經 commit，所以「寫嘅時候漏捉为」同「掃描器未驗證」係同一輪嘅兩截，唔係兩件無關嘅事。

`premium-tier.md` 其後寫咗「只可以放真正簡體專用字；中招要換字，唔好刪斷言」——呢條係事後紀錄，出事嗰格冇執行。

### 案 4　寫 9 篇漏第 4 段（少傳參數），要重寫

事實：

- 續寫 ESFP 9 篇嗰格（訊息 13626）用位置參數 helper：

```python
def a(k, spark, c1, c2, c3, g1, g2, s):
    P[k] = {"spark": spark, "clash": [c1, c2, c3], "give": [g1, g2], "sum": s}
```

- 執行結果（訊息 13627）：`TypeError: a() missing 1 required positional argument: 's'`，cell 第 13 行（第二個 `a()`，即 `ESFP|INTP`）。`s` 就係第 4 段 `sum`。
- 代理下一句（訊息 13628）：「手快漏咗幾篇嘅總結段（未寫入檔案）。重寫完整版。」重寫後先係 `今批: 9 篇 | 四段唔齊 0`，然後先 commit `ea257fb`。
- 檔案冇被寫入半套壞資料（throw 發生喺 `open().write` 之前）。成本係成批重寫，唔係上船壞文。

機制：

9 篇塞喺一個 positional call list。參數次序係 spark + clash×3 + give×2 + sum，sum 喺每篇最後，抄下一段最易掉。冇「組完先 assert 每篇有 `sum`」；唯一守門係 Python 簽名爆炸。爆炸係 fail-closed，所以未上船，但代理要靠記憶重寫成批——重寫本身又係同一種未檢查嘅批量生成。

事實同事後概括有張力：throw 喺第二篇，代理原文係「幾篇」，其後總結成「每篇」。機制一樣，範圍係「由某一篇起缺最後一個位置參數」，唔係已驗證嘅「9 篇全部缺」。

### 案 5　「結果頁排版錯」先猜 Tailwind、再猜 div 嵌套

事實：

- 用戶報排版錯之後、講「上下合埋」之前，代理嘅假設次序（訊息 13557–13573）：
  1. Tailwind CDN 改靜態 CSS 嘅版本／規則差（對應 `3cb7a48`、`c5aa0ab`，係之前嗰輪大改）。
  2. 搬 `#personalReport` 整到 div 不平衡（對應 `95de24b`，而且嗰輪代理確實抽多刪過一行 `#compatibility`）。
- 兩項都有硬證據洗清：CDN 規則對比「漏 0 條、內容唔同 0 條」；`#result` div 平衡 21/21，同搬位前一樣。然後先去裝 Playwright 想睇真排版。
- 用戶一句「配對頁同結果頁上下合埋」（訊息 13593）之後，下一格就鎖定 `#pair` 冇被 hidden（訊息 13594–13600）。修喺 `f7c1b1b`：`show()` 隱藏清單加 `"pair"`。
- 真根因同 Tailwind、同 div 嵌套無關。`page-navigation.md` 當時已有：「新增分頁必須加入 `show()` 隱藏清單，否則兩頁疊埋」。配對頁係新 `<section id="pair">`。

機制：

「排版錯」係低資訊症狀。代理冇先做一個分辨實驗（邊幾個 `section[id]` 冇 `hidden`），而係由「我最近改過咩」起假設。最近兩次大改剛好係 CSS 交付同搬卡，兩件都曾經搞壞過排版，所以優先級被近期創傷佔用。jsdom 冇 layout，CSS diff 同 div 計數都答唔到「兩個畫面係咪同時可見」。用戶嗰句同時畀咗兩個 section 名同空間關係，等於直接講咗分辨實驗嘅預期結果，所以定位由「洗清兩條假假設」變成一步。

推測：若第一個 probe 係「列出可見 section」，唔使等用戶第二句，亦唔使裝瀏覽器。本部當時冇 Chromium（裝 Playwright 失敗／下載中），用瀏覽器追排版係慢路徑，而且唔係呢個 bug 嘅必要條件。

### 案 6　只睇 `show` 第二個定義（wrapper）

事實：

- `index.html` 有兩個 `window.show = function`：L3227 真身（L3251 先係隱藏清單，含 `"pair"` 係 `f7c1b1b` 之後先補），L5251 wrapper：

```js
const _origShow = window.show;
window.show = function(id){
  _origShow(id);
  if(id === "result"){ try{ setShareHint(); }catch(e){} }
  if(id !== "test"){ try{ stopQuestionVoice(); }catch(e){} }
};
```

- 執行時後者靜默覆蓋前者，但清單喺前者。只讀後者（代理自述約 162 字）會結論「show 唔負責隱藏畫面」。
- 代理事後寫入 `page-navigation.md`：「只睇後面嗰個會完全睇唔到清單」。`premium-tier.md` 陷阱 9 早已記錄同型問題（`goPickVersion` 定義兩次，後面靜靜贏）。
- 用戶講「上下合埋」之後，代理先 `finditer` 全部 `show = function`（訊息 13596），先至對到兩個 body。

機制：

單檔巨型 script 允許同名函數後寫覆蓋，冇語法錯誤。代理查「結果頁顯示時做咩」會自然落到 L5249 註釋「結果頁顯示時更新提示」下面嗰個短 wrapper——因為佢就喺結果頁相關碼旁邊，而且係 runtime 真正被呼叫嘅那個。短、近、係「贏咗嘅定義」，三個理由都支持「讀呢個就夠」。清單喺佢呼叫嘅 `_origShow` 入面，唔展開 callee 就睇唔到。所以案 5 嘅假假設可以維持很久：你讀緊嘅 `show` 根本冇隱藏清單，自然會去 CSS／DOM 度搵「排版」。

## 2. 共同模式

| # | 模式 | 對應個案 | 點解呢種做法會產出呢個錯 |
|---|---|---|---|
| P1 | 未驗證嘅假設當事實 | 2、3、5 | 未寫配對、簡體清單、Tailwind／嵌套，都係「合理」但未用一個會否證嘅對照跑過就拿去決定 |
| P2 | 工具輸出求快，揀順耳嘅訊號 | 1、3 | rc 1 同「✗ 冇 ✓」同時在；24 個命中同「no-op」同時在。順耳嗰個被當成結論 |
| P3 | 驗證唔係出貨閘門 | 1（3 嘅內容亦係掃描前已 commit） | 測試、commit、push 同一格順序執行；外層工具成功 ≠ 內層 rc 0 |
| P4 | 冇單一真相，讀局部當全部 | 2、6 | 測試寫死一個會變嘅 key；函數讀最後／最近嗰個定義，唔數全部 |
| P5 | 批量生成冇逐項結構檢查 | 4 | 位置參數最後一格最易掉；唯一回饋係整格 throw，然後靠記憶重寫 |

五個模式係一條鏈：P1 產生錯的物件 → P4 令你睇唔到全貌 → P2 把紅訊號解讀走 → P3 令紅訊號唔會停手 → P5 令內容批次喺閘門之前已經成形。案 1+2 係 P3+P1+P4 一齊爆；案 5+6 係 P1+P4；案 3 係 P1+P2+P3；案 4 係 P5（幸而 fail-closed，未過 P3）。

## 3. 流程修正（可寫入工作守則）

每條都係：觸發 → 動作 → 點解有效。動作要係代理自己做得到嘅命令或腳本分支，唔係「小心啲」。

### R1　出貨腳本硬閘

- 觸發：任何會 `git commit` 或 `git push` 嘅腳本。
- 動作：測試同 push 拆開。測試格印每個命令嘅 exit code 之後必須 `if rc != 0: raise SystemExit(rc)`，下一格先准 `git add`。禁止「跑完測試順手 push」寫喺同一個 `execute_code` 而冇 early-exit。`execute_code` 自己 `status: success` 唔算出貨許可。
- 點解有效：案 1 嘅腳本係印完 `rc: 1` 仍然 push；外層成功掩蓋內層失敗。硬閘令「想快」都過唔到，唔使靠記得。

### R2　「有 N 個測試檔失敗」＝打開嗰個檔，唔好再解讀摘要

- 觸發：`run.sh` 最後一行含「有 N 個測試檔失敗」，或任一 `*_test.js` rc ≠ 0。
- 動作：唔好用「輸出有冇 `✗`」判決。逐個再跑：

```bash
cd /opt/data/repos/hk-mbti
export NODE_PATH="$PWD/tools/ui/node_modules"
for t in tools/ui/*_test.js; do
  node "$t" >/tmp/t.out 2>&1
  ec=$?
  [ "$ec" -eq 0 ] || { echo "FAIL $ec $t"; sed -n '1,40p' /tmp/t.out; break; }
done
```

第一個非 0 嘅檔，讀 exception 或第一行 `✗`，修完該檔 rc 必須 0，再跑全套。全套 rc 0 之前唔准 commit。

- 點解有效：陷阱 8 嘅 throw 冇 `✗`。案 1 正是「✗ 冇」同「1 個檔失敗」打架，摘要層解決唔到，只有重跑單檔先見到 `INTJ×ESTJ` 那條斷言。

### R3　測試唔准寫死「而家未有嘅內容」

- 觸發：新斷言涉及「未寫／未解鎖／篇數 === N／某一對型號」。
- 動作：預期狀態由資料檔計出，唔好寫死 key。配對未寫路徑用而家 `pair_test.js` L60–67 嗰種動態搜。若一定要寫死一對，斷言只准測 schema（4 段齊），唔准測「呢對唔存在」。落測試前 grep 自己檔：`openPair("` 同 `=== 16` 之類，每條寫一句「內容加一批之後呢條會唔會自己紅」。會就改掉先准 commit。
- 點解有效：案 2 嘅斷言壽命等於下一個內容批次。動態搜令「寫咗 ESTJ」唔會破壞「未寫要有提示」呢條合約。

### R4　手寫掃描清單先過正負對照，先准用

- 觸發：要加簡體字、emoji、禁詞等手寫清單，或者用清單做 replace。
- 動作：
  1. 清單只准「繁簡不同」嘅單字。詞（「处理」）禁止直接丟入字元類。
  2. 負對照：對一份已知繁體樣本（例如現有 `pair-data.js` 入面已審過嘅 INFP 行）跑，命中數必須印出 `0`。
  3. 正對照：樣本加一個 `为`，命中數必須印出 `1`，而且命中字係 `为` 唔係 `理`。
  4. 兩行數字未印出之前，唔准用呢條清單 replace，亦唔准當守門。假命中要換字，唔好刪斷言，亦唔好當 no-op 收科。
- 點解有效：案 3 失敗係因為 `理` 從未被「繁體正文必須 0 命中」否證。正對照保證真簡體字唔會因清單太窄而漏。

### R5　批量文章用 dict + 寫入前逐篇 assert

- 觸發：一格要寫超過 1 篇配對／章節。
- 動作：唔好用位置參數 `a(k, spark, c1, c2, c3, g1, g2, s)`。每篇一個 dict。`open().write` 之前印：

```text
缺欄: 0
clash 唔係 3: 0
give 唔係 2: 0
```

任一非 0 就 raise，唔好重寫成批碰彩。throw 之後只補缺欄嗰幾篇，唔好靠記憶重生成 9 篇。

- 點解有效：案 4 嘅 `s` 係最後一個位置參數，抄塊必掉。dict 缺 key 會在組裝時按篇報名，唔使成格炸掉再重寫。

### R6　UI 症狀先做分辨實驗，兩次假假設就停

- 觸發：用戶報「排版錯／疊／找不到／空白」，而症狀冇講明 section。
- 動作：第一個 probe 只做兩件事，未做完唔准改 CSS、唔准對 Tailwind：
  1. jsdom 打開相關流程，印所有 `section[id]` 入面冇 `hidden` 嘅 id。多過一個就係互斥 bug，去 `show()` 清單，唔好去 CSS。
  2. 印 `window.show = function` 嘅次數同每個 body 嘅行號（見 R7）。
